# 设计调研与决策记录

决策日期：2026-07-17。

## 方案对比

| 项目或标准 | 有用的想法 | 为何不构成 VibeBus 的核心 |
| --- | --- | --- |
| [mco-org/squad](https://github.com/mco-org/squad) | 轻量级多智能体协作与宽松的参考实现 | VibeBus 必须保留独立的 Codex 顶层任务和原生 Windows 操作，而不是采纳另一个编排外壳 |
| [MCP Agent Mail](https://github.com/Dicklesworthstone/mcp_agent_mail) | 定向收件箱、确认和文件路径预留行为 | 其实现与许可约束不作为代码库使用；VibeBus 在 Rust 中独立实现该行为 |
| [Beads](https://github.com/steveyegge/beads) | 持久化问题图和感知依赖的工作 | 其更宽泛的问题跟踪器和面向 Dolt 的存储模型增加了运维负担；VibeBus 只需要一个小型多进程 SQLite 作为唯一事实来源 |
| [A2A protocol](https://github.com/a2aproject/A2A) | 可互操作的任务与制品语义 | A2A 面向网络化智能体互操作；VibeBus 刻意采用本地优先（local-first）和项目范围限定 |
| 原生 Codex 任务与工作树 | 正确的隔离、用户可见的任务所有权、原生 UI | 它们仍然是执行边界。VibeBus 对其增强而非取代 |

## 选定的综合方案

选定的设计是一个轻量原生 Rust 二进制，每个项目对应一个 SQLite WAL 数据库，通过 CLI 和 MCP 暴露，并以 Codex 插件形式分发。

该组合保留了参考实现中最强的特性：

- 来自邮箱式协作的收件箱与确认（ACK）语义；
- 来自任务图系统的原子所有权与依赖关系；
- 与更广泛智能体协议兼容的制品形态产出；
- 原生 Codex 任务与工作树隔离；
- 无需本地守护进程的小型可审计部署面。

## 已否决的备选方案

- 共享的 Markdown 或 JSON 文件：并发写入能力弱、无原子认领、diff 噪音大，且会意外耦合仓库。
- 以单个 Git 分支作为消息总线：合并延迟和冲突会掩盖运行状态。
- 本地 HTTP 服务：引入额外的生命周期、端口、防火墙、认证和崩溃恢复问题，却没有带来 MVP 收益。
- 直接操作 Codex 内部任务状态：不稳定且超出产品边界。
- 全量对话记录同步：成本高、隐私负担重，且有悖于独立任务隔离。

## 兼容性方向

未来的网络或 A2A 桥接应从事件与制品模型出发进行转换。它们必须保持适配器（adapter）角色；本地 SQLite 事实对 VibeBus 项目而言仍是权威。

## 发布工程决策

0.7 版本发布切片对比了四种 Windows 分发形态：

| 方案 | 优势 | 决策 |
| --- | --- | --- |
| 仅便携 ZIP | 无安装器依赖，易于检查 | 保留作为回退方案，但不足以处理 PATH 与卸载生命周期 |
| MSIX | 强大的平台身份与签名模型 | 暂缓，因为本地/私有分发需要证书身份和部署策略，会使 MVP 复杂化 |
| Inno Setup 或 NSIS EXE | 灵活的 UI 与脚本能力 | 暂不采用，因为自定义脚本会扩大安装器的攻击面与维护面 |
| WiX MSI | 原生 Windows Installer 升级/卸载语义与内置 ICE 校验 | 选定，采用明确的按用户（per-user）、无自定义操作的包 |

先测试了 WiX 7.0.0，因为它是当前版本，但其命令行工具要求显式接受 OSMF EULA。VibeBus 不会代替维护者自动接受法律条款，因此仓库在其公布的 MS-RL 许可下锁定 WiX 4.0.6。v4 模式与命令行流程已覆盖所需的 MSI，无需扩展。

签名方面，选定的基线方案是 SignTool 配合仅以 GitHub Secrets 存储的 CA 签发 PFX。该方案与提供方无关，且可用于 GitHub 托管的 Windows 运行器。生产工作流在构建 MSI 之前对可执行文件签名，之后对 MSI 签名，并校验两者。当证书操作有必要时，云签名或硬件支持的签名仍可作为可替换的适配器。

## 破坏性维护授权决策

0.8 版本对比了三种留存授权形态：

| 方案 | 优势 | 决策 |
| --- | --- | --- |
| 智能体令牌加上类型化的计划 ID | 简单且已实现 | 否决其作为唯一门禁，因为同一个自主调用方既能规划也能删除 |
| 通过 MCP 或命令行参数传递长期有效的操作员密钥 | 易于自动化 | 否决，因为这会把这更强的能力放入模型可见的输入中，并消除有意义的分离 |
| 以短期数据库能力存储的交互式 CLI 审批 | 将规划与本地操作员同意分离，同时不向 MCP 暴露密钥 | 选定 |

选定的流程在保持 SQLite 权威性的同时，增加了一道程序性的人工在场边界。操作员的初始化、轮换、保险库恢复和审批都要求在真实终端中进行，并输入完全匹配的确认。密钥存储在一个独立的 Windows 凭据管理器目标中；数据库仅存储其摘要和代数（generation）。审批将精确的计划 ID、策略、有效期和操作员代数绑定在一起。Apply 步骤将其与清理和报告存储一起原子性消费。

这里刻意不声称能防范已经以同一 Windows 用户身份运行的恶意进程——这样的进程处于当前的本地信任边界之内。该能力用于防止常规的 MCP/智能体工作流和被重定向的自动化意外授权破坏性维护，同时为硬件支持或多方审批保留清晰的未来适配点。
